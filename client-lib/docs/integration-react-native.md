# Integration guide — React Native

The same client every binding exposes (`api.md` describes every method), as a
React Native library (a turbo module). It is generated by
[`uniffi-bindgen-react-native`](https://jhugman.github.io/uniffi-bindgen-react-native/)
from the very same UniFFI crate Kotlin and Swift come from
(`bindings/uniffi`), so React Native gets the same API — `TrafficNetworkClient`
with `call`, `callAsync`, an event listener, realtime push and a host-implemented
`SecureStore` — not a port of it. Nothing is hand-written on top.

**What you need:** Node 22 with Yarn 4 (`corepack enable`), a Rust toolchain
(with the Android targets and `cargo-ndk` for Android, the iOS targets for iOS —
see `integration-android.md` and `integration-ios.md`), the Android SDK with an
NDK and JDK 17 for Android, a Mac with Xcode and CocoaPods for iOS. Nothing is
published to npm yet; you build the library from this repository.

## Build the library and its example app

All paths are relative to `client-lib/`. A React Native library is a lot of
boilerplate (Android and iOS projects, codegen configuration, an example app)
that `create-react-native-library` writes better than we could keep up to date,
so it is generated rather than checked in; `scaffold.mjs` runs it with pinned
versions and adds what is ours.

```bash
# 1. The library skeleton → bindings/react-native/library/
node bindings/react-native/scaffold.mjs

cd bindings/react-native/library
corepack enable
yarn install

# 2. The Rust for Android (4 ABIs) and/or iOS (on a Mac), and the TypeScript
#    and C++ bindings generated from it.
yarn ubrn:android
yarn ubrn:ios

# 3. React Native's own codegen, the JavaScript build, the type declarations.
yarn prepare

# 4. iOS only: the pods, after the codegen (they list the files it wrote).
yarn ubrn:pods

# 5. The example app (needs an emulator/simulator or a device).
yarn example android
yarn example ios
```

`ubrn.config.yaml` points `uniffi-bindgen-react-native` at `bindings/uniffi` —
change the Rust and run `yarn ubrn:android` again, and the TypeScript follows.

The scaffold makes one change to what `create-react-native-library` writes:
its template registers the library's CMake project with the app as a C++ turbo
module, but the library that `uniffi-bindgen-react-native` generates is a classic
Android module with its own `build.gradle` that builds that CMake project itself —
registering it twice builds the same code twice and the app's copy looks for a
header that does not exist — so `scaffold.mjs` removes the `cxxModule*` entries
from `react-native.config.js` (and fails if the template no longer has them).

## The smallest possible use

```tsx
import { DocumentDirectoryPath } from '@dr.pogodin/react-native-fs';
import { TrafficNetworkClient } from '@trafficnetwork/react-native';

const client = new TrafficNetworkClient(
  JSON.stringify({
    storagePath: `${DocumentDirectoryPath}/trafficnetwork`, // database + secrets live here
    discovery: false,
    nodes: ['https://node.example.org'],
    credentials: { type: 'client', clientId: '…', clientSecret: '…' },
  }),
  undefined, // or a SecureStore of yours
);

// Every call is  callAsync(method, argsJson) -> resultJson,  {"ok": …} or {"error": …}.
const here = JSON.stringify({ lat: 52.52, lng: 13.405 });
await client.callAsync('updatePosition', here);   // which map tiles to watch
await client.callAsync('sync', '{}');             // fetch what is around
console.log(await client.callAsync('getSpeedLimitAt', here)); // local, instant

client.uniffiDestroy(); // releases the client; its data stays on disk
```

`bindings/react-native/overlay/example/src/App.tsx` is this as a complete screen
(replace the three constants at its top first). The app needs a directory to give
the client — React Native itself does not expose one, so the example uses
`@dr.pogodin/react-native-fs`'s `DocumentDirectoryPath`; `expo-file-system` works
the same way.

Things an app usually wants on top of that:

- **Use `callAsync`, not `call`.** `call` blocks the JavaScript thread until the
  call is done — for a sync, as long as the network takes. `callAsync` returns a
  `Promise` and runs on the library's own threads.
- **Errors:** `callAsync` never rejects for an ordinary failure; it resolves
  with `{"error": {"code", "message"}}` and one of the API's codes (`api.md`,
  "Errors"). Only the constructor throws (`ClientError.Failed`, with
  `errorCode` and `detail`) for options it cannot use.
- **Keep it fresh:** call `tick` from a timer; it is cheap and syncs only when
  due. Nothing runs by itself.
- **Live updates:** `client.startRealtime()` keeps a WebSocket open on the
  library's own background task; `client.setEventListener({ onEvent(json) {…} })`
  tells you when data changed.
- **Your own secret store:** pass an object implementing `SecureStore`
  (`get(key)`, `set(key, value)`, `delete(key)`) as the constructor's second
  argument, and the device's credential and signing key go there instead of
  into a file in `storagePath`. **It must answer synchronously** — the library
  asks from one of its threads and waits for the JavaScript to return — so a
  Keychain/Keystore plugin that only offers promises cannot back it directly
  (a synchronous store such as an encrypted `react-native-mmkv` can). Without
  one, secrets live in a file in the app's private directory.
- **Finish:** `client.uniffiDestroy()`.

## How it behaves

- **Calls run on the library's own threads** (8 MiB stacks) — the JavaScript
  thread only waits for the Promise.
- **A crash never reaches you as one:** a panic inside the library becomes an
  `internal` error result; a `SecureStore` or listener of yours that throws
  answers "not there"/"refused" (store) or is ignored (listener).
- **TLS** trusts the Mozilla root certificates bundled in the library, not the
  platform's store — see `api.md`, "Network & privacy".
- **Storage** is SQLite on the device, written synchronously — the same store as
  the native bindings.

## Verified in CI

- `react-native-android` (Linux): the scaffold, `yarn ubrn:android` (the Rust
  built for the four Android ABIs and the TypeScript/C++ bindings generated),
  `yarn prepare` (React Native codegen, JavaScript build, type declarations), a
  TypeScript type-check, and the example app built (`assembleDebug`).
- `react-native-ios` (macOS runner): `yarn ubrn:ios` (the Rust for the iOS
  targets as an XCFramework, the bindings), `yarn prepare`, `yarn ubrn:pods`, and
  the example app built for the iOS simulator.
- Underneath, the Rust crate and the API it exports are the ones the Kotlin and
  Swift runs of `conformance/scenarios.json` exercise.

**Not verified in CI, said plainly:** the example app is *built*, not *run* —
nothing executes on an Android or iOS device, emulator or simulator — and the
conformance scenarios are not run *through React Native*. The generated
TypeScript/C++ layer (JSI) is the one part of this binding that no test here
exercises at run time. The tooling is young (`uniffi-bindgen-react-native`
describes itself as early in development, and this library follows the newest
React Native), which is why every tool version in `scaffold.mjs` is pinned.
